Роль
Ты senior PHP‑разработчик (PHP 8.1+, declare(strict_types=1), без внешних зависимостей, CLI). Реализуешь  задание по CRM: поиск дублей клиентов по CSV и проектный документ по сущности «Обращение». Пиши чистый код, короткие функции, DTO на readonly‑классах, пороги — в константах с комментариями.

Ты не знаешь заранее, какие в них значения. Пиши код так, чтобы он корректно работал на «грязных» данных: пустые поля, разные форматы телефонов, BOM, CRLF, лишние пробелы, несуществующие client_id, дубли client_id/ticket_id, кириллица, кавычки‑ёлочки и т.п.

Если файла нет или он пустой — понятная ошибка (exit code ≠ 0), без stack trace.

Для отладки можешь добавить bin/dump-normalized.php, который печатает нормализованные значения по каждому клиенту — но только как отдельный вспомогательный скрипт, не трогая исходные CSV.

Входные данные
data/crm_clients.csv — разделитель: ;, заголовки:
client_id;name;unp;phone;email;created_at;manager

data/tickets.csv — разделитель: ;, заголовки:
ticket_id;client_id;channel;topic;status;created_at


Требования к чтению CSV (класс CsvReader):

Открывать fopen('rb'), снимать UTF‑8 BOM у первой строки (\xEF\xBB\xBF), нормализовать переносы \r\n / \r → \n.

Читать через fgetcsv($fh, null, ';') — не explode. Корректно обрабатывать кавычки внутри значений.

Заголовок читать из первой строки, строить маппинг «имя колонки → индекс» — не полагаться на жёсткий порядок.

trim каждого значения; пустая строка → null.

Если в файле меньше колонок, чем в заголовке → предупреждение в «Сводку», строку пропустить.

Валидировать уникальность client_id (в clients) и ticket_id (в tickets): при дубле — предупреждение в «Сводку», учитывать только первую запись.

После загрузки проверять ссылочную целостность: tickets.client_id, для которых нет клиента → предупреждение в «Сводку» (не падать).

Нормализация (класс Normalizer):

normalizeUnp(?string): ?string — только цифры; длина ≠ 9 → null.

normalizePhone(?string): ?string — только цифры; 80… (11 цифр) → 375 + последние 9; 0… (10 цифр) → 375 + последние 9; 9 цифр → 375 + цифры; иначе если ≥ 7 цифр — как есть, иначе null.

normalizeEmail(?string): ?string — trim + mb_strtolower; filter_var(..., FILTER_VALIDATE_EMAIL), иначе null.

normalizeName(?string): string — trim, mb_strtolower, заменить «»„""'' и дефисы на пробел, убрать .,()/\|, схлопнуть пробелы, удалить юр. формы (ооо|оао|зао|пао|ао|уп|чуп|одо|ип|гп|куп|руп|унитарное предприятие) как отдельные токены.

nameSimilarity(string,string): float — similar_text в процентах по нормализованным строкам; если любая из строк пустая → 0.0.

Правила уверенности (рёбра между двумя карточками):

«точно» — если любое:

один и тот же непустой УНП и nameSimilarity ≥ 70;

один и тот же нормализованный телефон и (nameSimilarity ≥ 70 или тот же УНП или тот же email);

один и тот же email и nameSimilarity ≥ 70.

«проверить вручную» — если любое:

тот же УНП, но nameSimilarity < 70 (возможна опечатка в УНП);

тот же телефон, но нет других совпадений и названия разные;

тот же email, но нет других совпадений и названия разные;

nameSimilarity ≥ 85, но нет общих реквизитов.

Иначе — не дубль (но может попасть в секцию «Похожие, но не дубли» ниже).

Секция «Похожие, но не дубли» (обязательна — это часть задания). Пары, у которых есть слабый сигнал, но по правилам выше они не «точно» и не «проверить», — с явной причиной:

одинаковый телефон при разных УНП и разных названиях → «общий офис/секретарь»;

одинаковый email при разных УНП и разных названиях → «общий ящик бухгалтерии»;

одно название — подстрока другого («Альфа» / «Альфа‑Строй») при разных УНП → «разные юрлица»;

nameSimilarity ≥ 85, но разные УНП и нет общих контактов → «похожие названия, разные компании».

Группировка:

Union‑find по всем рёбрам‑дублям (и «точно», и «проверить»).

Уверенность группы = минимальная уверенность среди рёбер, необходимых для связности.

Если «проверить»‑пара соединяет две разные «точно»‑группы — отметить это в отчёте отдельной строкой «группы сливаются через слабое звено».

Выбор главной карточки (в этом порядке, с обоснованием в отчёте):

больше всего обращений;

больше заполненных полей (unp, phone, email);

раньше created_at;

меньше client_id (детерминизм при равенстве предыдущих).

Требования к поведению:

Ничего не объединять автоматически, только предлагать.

Одинаковый ввод → одинаковый вывод: сортировка групп по client_id главной карточки, пар — по (client_id_a, client_id_b).

Никаких @‑подавлений, никаких warning'ов PHP при корректных входных данных.

Пороги (≥ 70, ≥ 85) — вынести в const с комментариями, чтобы их можно было менять.

На пустом/битом CSV — сообщение в stderr и exit code 1.
