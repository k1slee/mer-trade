# 06-improvement.md — Мониторинг обмена с 1С

## 1. Проблема и кто страдает

Обмен с 1С периодически «встаёт» (сеть, агент, права, блокировка, ошибка API маркетплейса).
Узнаём об этом от бухгалтерии  через несколько часов

Страдают: бухгалтерия (пересчёт), менеджеры (неверные цены/наличие), склад (остатки),
клиенты (обещали — не привезли), support и разработчики (реактивный разбор вместо плановой работы).

Почему сейчас так: обнаружение зависит от человека, лог никто не читает в реальном
времени, метрики MTTD (времени до обнаружения) нет.

## 2. Решение

**`exchange-watcher`** — read-only скрипт по cron каждые 5 минут. Группирует события
по направлению (`site→1c`, `1c→site`, `1c→marketplaces`, `wms→1c`, `1c→wms`),
применяет 4 правила, шлёт алерт в Telegram с контекстом, дедуплицирует по состоянию.

Правила:

| # | Условие | Severity |
|---|---|---|
| R1 | возраст последнего успеха ≥ 60 мин | CRITICAL |
| R2 | возраст последнего успеха ≥ 20 мин | WARNING |
| R3 | ≥ 3 ошибок за 15 мин | CRITICAL |
| R4 | нет ни одного успеха | CRITICAL |

Как работает (что видит дежурный):

1. cron → скрипт читает источник (CSV/лог/таблица БД read-only).
2. Считает по каждому направлению: последний успех, его возраст, ошибки за окно.
3. Определяет severity по правилам.
4. Если severity изменился — шлёт в Telegram: направление, время последнего успеха,
   5 последних строк ошибок, ссылка на runbook.
5. Сохраняет состояние в `state.json` — повторно не спамит.
6. Раз в сутки — digest: сколько инцидентов, средний MTTD.

**Вне рамок MVP:** автоперезапуск обмена, запись в 1С, интеграция с Jira,
чтение ПДн/сумм в алертах.

## 3. Метрики «до/после»

| Метрика                              | До             | Цель после                         | Как мерить                                        |

| MTTD (время до обнаружения)          | 2–4 ч (жалоба) | ≤ 15 мин                           | медиана `ts_alert − ts_first_error` по инцидентам |
| Доля инцидентов, найденных до жалобы | ~10%           | ≥ 90%                              | доля алертов раньше первого тикета                |
| Средний простой обмена               | часы           | ≤ 1 ч                              | `ts_fix − ts_first_error`                         |
| Ложные срабатывания                  | —              | ≤ 2/нед                            | ручной журнал дежурного                           |

## 4. План внедрения

**День 1**
- интервью с бухгалтерией и админом 1С: где лог, что считается «успехом»;
- baseline за 2 недели: сколько инцидентов и какой сейчас MTTD;
- прототип на фейковых данных, согласование порогов.

**Неделя 1**
- подключить реальный источник read-only (файл / таблица / лог);
- скрипт + cron, отправка в тестовый Telegram-чат;
- runbook: кого звать, что проверить, как перезапустить;
- dry-run 3–5 дней: не мешаем, только смотрим на алерты.

**Неделя 2**
- прод: алерты в рабочий чат дежурного;
- калибровка порогов по факту (ложные срабатывания / пропуски);
- дедуп по направлениям, ежедневный digest;
- замер «после», ретроспектива, передача дежурному.

## 5. Риски и снижение

| Риск                                                   | Снижение |

| Нет прямого доступа к логу 1С                          | Косвенные признаки: `mtime` файла обмена, healthcheck-endpoint, read-only `SELECT` из `_ExchangeLog` |
| Ложные срабатывания (ночные окна, регламентные работы) | Whitelist окон, `--dry-run`, пороги 20/60 мин, ручное подтверждение первые 2 недели |
| Alert fatigue                                          | Дедуп по состоянию, severity, daily digest, максимум 1 сообщение на инцидент |
| Безопасность                                           | Только read-only, секреты в env, в алертах — без ПДн и сумм, только направление и код/текст ошибки |
| Скрипт сам упал                                        | Deadman-check: если watcher молчит > 2 циклов — алерт в тот же чат |

## 6. Где ИИ (вспомогательно, не в детекте)

- **Суммаризация ошибок.** В алерте 1–2 строки «что вероятно случилось» — модель
  выбирает из шаблонов runbook и цитирует лог. Так галлюцинации ограничены.
- **Классификация инцидента** (сеть / права / API маркетплейса / блокировка 1С)
  → тег в алерте, помогает дежурному быстрее выбрать ветку runbook.
- **Агент первого шага.** По кнопке «разобрать» собирает чек-лист из runbook
  и предлагает действия — **без автоматического выполнения** в прод.
- **Детект оставляем детерминированным.** ИИ не решает «сломалось или нет»,
  иначе получим ложные пропуски. ИИ — только надстройка над фактом алерта.

## 7. Прототип

`prototype/` — Python-скрипт без внешних зависимостей. Читает `fake_exchange_log.csv`,
печатает отчёт и алерты в стиле Telegram. Поддерживает `--now` (симуляция времени)
и `state.json` (дедуп). См. `prototype/README.md`.
